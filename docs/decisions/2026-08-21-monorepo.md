# Use a Polyglot Monorepo with Isolated Runtime Environments

## Status

Accepted for planning. Repository scaffolding has not yet been created.

## Context

The project contains tightly coupled artifacts across product and ML work:

- Python domain contracts and provider simulator;
- data generation and model training;
- Fast/Slow inference and evaluation;
- FastAPI and Temporal workers;
- a TypeScript web application;
- later email and voice adapters;
- shared scenario fixtures, schemas, and end-to-end tests.

Changes frequently cross these boundaries. For example, adding a field to `ProviderOffer` affects simulator output, training examples, the verifier, API contracts, UI comparison, and evaluation. Separate repositories would make these changes harder to review and reproduce at a one-person/small-team stage.

A single Python environment is also inappropriate. GPU training/serving packages and audio dependencies can conflict with the stable API/workflow runtime. The current `uv` documentation explicitly notes that one workspace is not suitable when members require conflicting environments.

## Decision

Use one Git monorepo with explicit dependency zones and more than one lockfile:

```text
proxyloop/
├── apps/
│   └── web/                         # Next.js; pnpm
├── runtime/
│   ├── pyproject.toml               # uv workspace root
│   ├── uv.lock
│   ├── services/
│   │   ├── api/                     # FastAPI control plane
│   │   ├── workflow_worker/         # Temporal workflows/activities
│   │   └── model_gateway/           # Fast/Slow typed adapters
│   └── packages/
│       ├── contracts/               # Pydantic canonical contracts
│       ├── telecom_domain/          # Pure business rules/verifiers
│       ├── agent_core/              # Safe observations/routing/gates
│       ├── provider_simulator/      # Fictional provider environment
│       └── connectors/              # Email/channel adapters
├── ml/
│   ├── pyproject.toml               # independent CUDA-aware uv project
│   ├── uv.lock
│   ├── data_pipeline/
│   ├── training/
│   ├── evaluation/
│   ├── serving/
│   ├── configs/
│   └── manifests/
├── voice/

│   ├── uv.lock
│   └── worker/
├── contracts/
│   ├── jsonschema/                  # generated, drift-checked artifacts
│   └── openapi/
```

### Tooling policy

- `uv` manages Python environments and locks.
- `runtime/` is one uv workspace because its packages share a Python version and compatible dependencies.
- `ml/` has its own lock so PyTorch, CUDA, flash-attention, and serving constraints cannot destabilize the runtime.
- `voice/` has its own lock so LiveKit/audio/native dependencies cannot destabilize the runtime or training environment.
- `pnpm` manages the web application and generated TypeScript client/types.
- A root `Makefile` exposes stable human/CI commands such as `make lint`, `make test`, `make contracts`, `make simulator`, and later `make dev`.
- Docker Compose runs local infrastructure; it is not used to hide incompatible dependency graphs.
- Do not introduce Nx or Turborepo initially. One web app and three explicit Python zones do not justify an additional build graph yet.

### Contract ownership

- Pydantic types in `runtime/packages/contracts` are the source for backend/domain contracts.
- JSON Schema and OpenAPI artifacts are generated into `contracts/` and checked for drift in CI.
- The web client/types are generated from OpenAPI; TypeScript does not manually redefine API payloads.
- Training manifests record the exact contract/schema version used to build examples.

### Dependency rules

- Domain contracts and pure business rules must not import FastAPI, Temporal, model SDKs, Gmail, or LiveKit.
- `agent_core` may depend on contracts/domain, but not on channel implementations.
- Services depend inward on packages; packages never depend on services.
- `ml/` may use local path dependencies for stable contract/domain packages or consume their generated schemas, but runtime services never import training code.
- `voice/` communicates through typed service/event contracts and does not import workflow internals.
- Web depends only on generated HTTP/event contracts.
- Large datasets, model weights, recordings, and runtime secrets are never committed.

## Alternatives Considered

### Multiple repositories

Rejected for the current stage. It would make contract changes, simulator/model comparisons, reproducible commits, and one-command CI harder without providing useful team ownership isolation.

### One repository and one Python environment

Rejected. Runtime, CUDA training/serving, and audio stacks have materially different dependency and hardware requirements.

### Nx or Turborepo from day one

Deferred. Either can help a large JavaScript-heavy monorepo, but the project is Python-first and initially has one TypeScript app. Root Make targets and scoped CI paths are sufficient.

### All-Python frontend

Rejected. A real approval/timeline/offer-comparison product benefits from a standard web stack, while keeping browser concerns separate from Python ML/runtime code.

### Polyrepo after the first demo

Possible later. A split becomes reasonable only when services have independent teams, release cadences, security boundaries, or scaling requirements. The contract and data-lineage artifacts must remain versioned across any future split.

## Consequences

### Benefits

- One commit can update simulator, data schema, model adapter, API, UI, and tests atomically.
- A portfolio reviewer can reproduce the whole system from one version.
- Shared fixtures and contract drift checks become straightforward.
- ML and product history remain connected without mixing runtime imports.
- Separate locks reduce CUDA/audio dependency conflicts.

### Costs

- Root commands and CI must understand several package managers/environments.
- Local path dependencies require disciplined boundaries.
- CI path filtering and caches need setup.
- A monorepo does not itself provide service isolation, deployment safety, or schema compatibility; those still require tests and versioned contracts.

## Validation Plan

Before the first feature implementation:

1. Install all three Python zones independently from their locks.
2. Install the pnpm workspace from its lock.
3. Generate JSON Schema/OpenAPI and TypeScript types from one sample Pydantic contract.
4. Run a contract round-trip test from Python serialization to TypeScript parsing.
5. Prove runtime unit tests do not import `ml` or `voice` packages.
6. Run CPU-only data/training smoke tests without installing production API or voice extras.
7. Record the commands and expected outputs in the runbook once scaffolding begins.

## Evidence

- `uv` workspaces provide shared lockfiles for compatible packages and document that conflicting requirements may need separate projects: https://docs.astral.sh/uv/concepts/projects/workspaces/
- pnpm provides native workspace support: https://pnpm.io/
- The project architecture and cross-boundary contracts are documented in `docs/architecture.md`.
